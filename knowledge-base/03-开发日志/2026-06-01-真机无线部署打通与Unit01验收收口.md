## 1. 真机无线部署：从 `unavailable` 到 `available (paired)`（关键配方，校正旧认知）

### 1.1 症状
设备 ChenHang（iPhone 15 Pro Max / iOS 26.4.2 / UDID `00008130-0008550E3E38001C`）在 `xcrun devicectl list devices` 一直 `unavailable`，解锁也不变；Xcode Devices 窗口 ChenHang 在「Disconnected」下、黄条「Browsing on the local area network」。用户没带线、以为同 Wi-Fi 即可（之前插线连过一次）。

### 1.2 根因 = 公司网客户端隔离
诊断 Mac 网络：`en0` IP `30.249.200.110`（园区大内网）、网关 `30.249.192.1`、**5 条 VPN 隧道 `utun0~4` UP**（零信任办公 VPN）。这类公司网几乎都开 **客户端隔离（AP isolation）**：同一 Wi-Fi 下手机和 Mac 互相看不见，Bonjour 能发现设备名（所以 Xcode 在 browsing）但**建立不了直连** → 永远 `unavailable`。路由器层隔离，本机改不了。

### 1.3 绕过 = 个人热点
让手机开「个人热点」、Mac 连上去 → Mac 切到 `172.20.10.11`（热点网段，无客户端隔离）→ 设备立刻 `available (paired)`。**没线也能无线部署的可靠路子 = 手机热点。**（公司 VPN 隧道若抢路由可临时断开零信任客户端，本次没断也通了。）

### 1.4 ⚠️ 校正旧 memory：CLI 能签真机（有现成有效证书时）
旧 `project_ios_app_status` / 05-31 日志写死「免费个人团队下 CLI 签不了真机，每次上真机=Xcode GUI Cmd+R」。**本次实测推翻这个绝对化结论**：

```bash
# 全部 CLI、无 Xcode GUI、全程走热点无线：
xcodebuild -scheme StarlightLiteracy \
  -destination "platform=iOS,id=00008130-0008550E3E38001C" \
  -derivedDataPath /tmp/sl-device -allowProvisioningUpdates build
#   → ** BUILD SUCCEEDED **
#   签名身份: "Apple Development: chenhangkobe@gmail.com (DW67YQ7QXU)"
#   描述文件: "iOS Team Provisioning Profile: cc.escapemobius.starlightliteracy.claude" (15d9631a-…)

xcrun devicectl device install app --device <UDID> /tmp/sl-device/Build/Products/Debug-iphoneos/StarlightLiteracy.app
#   → App installed (bundleID cc.escapemobius.starlightliteracy.claude)

xcrun devicectl device process launch --device <UDID> cc.escapemobius.starlightliteracy.claude
#   → Launched application
```

**校正后的准确认知**：
- 免费个人团队下，CLI **能**签+装+启动真机——**前提是钥匙串里已有一张有效的 `Apple Development` 证书 + 一份覆盖「本设备 + 本 bundle」的描述文件**（由之前某次 Xcode GUI `Cmd+R` bootstrap 生成，05-31 那次就生成了）。
- 之前 CLI 报 `No Account for Team` / `No profiles unable to generate` 的真实场景 = **冷启动、钥匙串里还没有可复用的证书/profile** 时，CLI 够不着 GUI 登录的 Apple ID session 去**新建**。
- 所以正确规律 = **GUI 只负责 bootstrap/续期证书与 profile（免费团队证书 7 天有效；或新增设备时）；一旦有了有效凭证，CLI 在有效期内能全自动签/装/启动**。不再是「每次都得 GUI」。

## 4. `上/下` 指事图重做（复审挖出的真设计缺陷，非凭感觉）

### 4.1 缺陷
旧 `上/下` scene 图（黄气球漂上方 / 蓝水滴向下落）**方向感是靠"物体在画面上方/下方"的构图位置**表达的——但抠图管线把主体**居中裁切**，位置线索被裁掉，贴纸里只剩气球/水滴，看图认字时孩子读到的是「气球/水滴」不是「上/下」。

### 4.2 修法 = 方向内嵌进物体
改成**小朋友食指向上 / 向下的手**（拳头 + 食指竖起指上/指下）——方向是物体自带的、裁切裁不掉，且正好对上 story「用手指头指天花板 / 地板」。落地：
- **替换** `tools/recognition-video/scripts/build-scene-assets.mjs` 的 `SUBJECTS.shang` / `SUBJECTS.xia`（气球/水滴 prompt → 食指手势 prompt，强调"解剖正确、恰好五指"防崩手）。
- 跑 `node build-scene-assets.mjs --only shang,xia --force`（aicodewith proxy + gpt-image-2 + magenta chroma → PIL 抠透明）。
- **人眼审 rendered 图**：两张手**渲染干净、解剖正常、不崩手、方向一目了然**（下带个小毛衣袖口）；边缘淡品红余边经核查与现有 18 张同一基线（脚本本身已带 despill `B>G` 压制），无需单独处理。
- 同步 iOS：手动 magick 把 `scene-assets/shang.png` / `xia.png` 按脚本同参数（`-background none -density 384 -resize -gravity center -extent -depth 8`）缩成 `scene_shang` / `scene_xia` 三档（256/512/768）。**只动该动的两组**，不跑全量 `generate-ios-image-assets.mjs`（避免它从 SVG/源图重渲覆盖 23:xx 手工产的 `scene_yi`/`oracle_shou` 引入无关 diff）。
- 重建 `_overview.png`（magick montage 5×4，全 20 字带新手势）。
- 旧图备份在 `tmp/scene-polish-backup/`（shang/xia 正图 + raw），可回滚。

### 4.3 `小` 经论证**保持**（非偷懒）
`小`（芝麻/小芽）不改，理由：① 匹配 story「看看米粒、沙子、芝麻」；② `上/下/手` 已是 3 只手，`小` 若再做手势（如捏小），看图认字里 4 只相似手会互相干扰、反而更难辨 → `小` 留作非手、辨识度独立那一个。用户若坚持改再动。
